# 智语项目演进对比

本文以仓库最早的 `main` 根提交 `1b5bdc0` 为基线，对比当前实现。对比只描述代码中已经落地的能力，不把规划项写成现状。

## 总体变化

| 维度 | 最早 main（`1b5bdc0`） | 当前实现 |
| --- | --- | --- |
| 产品形态 | 静态 HTML 语音笔记助手 | React 本地优先 AI Wiki |
| 知识主数据 | notes、文档索引与 Markdown 职责并存 | Markdown 当前正文 + SQLite 元数据/版本/任务 |
| 页面模型 | 笔记与文档分散入口 | 统一页面服务、版本、链接、反向链接 |
| 索引一致性 | 启动同步与业务流程直接更新 | 持久化索引任务、退避重试、重启恢复 |
| 检索链路 | 单查询 BM25 + Embedding + RRF + Reranker | 父子分块、多查询统一 RRF、单次精排、Token 预算 |
| Agent 编排 | 手写 Plan -> Execute -> Respond | LangGraph + Query Rewrite + CRAG + 证据门禁 |
| Agent 运行 | 请求内同步等待，流式输出需要二次生成 | 独立 Run、单次真实流、类型化事件、续传、取消、超时与终态恢复 |
| 写入安全 | Agent 直接执行写工具 | 预览、用户确认、幂等执行 |
| 外部知识 | 无受控联网闭环 | Search/Fetch 白名单 MCP、来源快照、确认入库 |
| 会话摘要 | 摘要后删除旧消息 | 增量摘要游标，原始消息完整保留 |
| 模型可靠性 | 单模型直接调用 | 可选主备故障转移、Token 与成本统计 |
| 可观测性 | 请求日志与总耗时 | request_id、阶段时间线、检索统计、运行记录、可选 Langfuse/OTel |
| 生命周期 | FastAPI startup 事件和未统一管理的任务 | lifespan 统一迁移、恢复、Worker 启停 |
| 代码组织 | API、Agent 调度与工具实现集中在少数大文件 | Agent 子路由、运行时、执行调度、工具注册和 React 状态/展示分层 |
| 测试 | 脚本和模型依赖型测试为主 | 单元测试、真实 API 集成测试、离线检索评测和前端构建 |

## RAG 链路变化

最早版本已经具备 BM25、Embedding、RRF 与 Reranker，这是当前系统保留的技术基础。主要问题是每个查询独立完成整条检索链路，多查询改写会重复精排，且召回片段和生成上下文使用同一粒度。

当前链路将两个问题拆开：

```text
细粒度子块负责召回
        |
        v
稳定父块负责精排、上下文和引用
        |
        v
所有改写查询统一融合，只精排一次
```

这个改动不替换 RRF、CRAG 或证据门禁，而是在它们之前改善召回，在它们之后增加上下文预算。因此旧能力没有被破坏，关闭 `RAG_V2_ENABLED` 还能回退到原链路。

## 数据与异步边界

当前数据库仍是 SQLite，SQLAlchemy 使用同步 Session。异步能力主要位于 FastAPI 路由、MCP 调用、Agent 执行编排和后台 Worker，而不是数据库驱动本身。

这是个人项目的主动取舍：

- SQLite 降低部署成本，适合本机单用户数据量。
- 页面写入和索引通过持久化任务解耦，模型故障不影响正文保存。
- 若进入多用户高并发场景，需要迁移 PostgreSQL、异步驱动、独立任务队列和权限模型，不能只把 SQLite 连接改成 async。

## Agent 运行边界

最早版本将一次 Agent 调用等同于一次 HTTP 请求，连接中断、并发请求和执行超时没有独立状态。当前实现把 Run 从连接生命周期中拆出：同一会话限制一个活动 Run，前端按事件序号消费单次模型流，断线后从最后序号续传，停止和总超时都会产生明确终态。

活动事件仍放在进程内，终态批量写入 SQLite，这是针对个人单实例项目的成本取舍。它解决了面试项目最需要展示的运行一致性与可恢复语义，但不冒充分布式任务系统；横向扩展时应引入共享事件流、分布式会话锁和独立执行 Worker。

## 没有改变的核心

- 项目仍以个人学习和课堂知识沉淀为目标，没有包装成多租户 SaaS。
- BM25、Embedding、RRF、Reranker 仍是本地检索基础。
- Markdown 仍保持可读、可迁移和可备份。
- 模型不能绕过证据门禁或用户确认直接修改知识库。
- MCP 是证据不足后的显式分支，不是默认自动联网。

## 面试表达

可以把项目差异概括为：

> 我没有把它做成一个套壳聊天页面，而是围绕个人 Wiki 的数据一致性、可信 RAG 和可恢复执行设计完整链路。检索采用父子分块与多查询统一融合，生成前保留 CRAG 和证据门禁；Agent 使用单次真实流和可续传 Run，知识写入与外部研究都必须确认。SQLite 和本地模型是个人部署的成本选择，但索引任务、模型网关、运行记录和迁移边界按可演进方式实现。
