# RAG 评测设计思路

## 目标

智语通过固定数据和逐级消融回答以下问题：

1. 关键词与语义改写能否命中真实证据；
2. BM25、Embedding、RRF 和 Rerank 分别带来什么收益；
3. 多证据和相似概念场景是否能够正确召回；
4. 在线模型的质量收益是否值得其延迟和调用成本；
5. 无答案或错误前提问题能否进入正确的证据门禁分支。

## 数据边界

评测数据分为两部分：

```text
corpus.jsonl     可检索的真实知识分块
questions.jsonl  问题、期望动作与证据标签
```

它们不是训练集和测试集。系统不使用 Question 训练模型，而是使用冻结的问题集检查不同检索方法在同一语料上的表现。

公开仓库不提交私有知识库、完整 Question 或逐题报告。`data/eval/` 由 Git 忽略，只公开评测代码、数据契约和不包含私人内容的小型示例。

## Question 类型

| 类型 | 验证重点 |
| --- | --- |
| `keyword` | 专有名词、缩写和精确配置项 |
| `semantic_rewrite` | 用户表达与文档措辞不同的情况 |
| `multi_evidence` | 一个问题依赖多个事实或父块 |
| `similar_concept` | 知识库中相近概念的区分 |
| `unanswerable` | 拒答、纠正前提或外部研究路由 |

正例包含相关父块、参考答案和原文证据；无答案样本不能伪造 `relevance`、`reference_answer` 或 `evidence`。

## 证据约束

Golden Question 采用“模型负责语言表达，程序负责事实边界”的方式生成：

1. 程序从真实父块提取候选证据 Span；
2. LLM 通过 Function Calling 选择已有证据 ID 并生成问题；
3. 程序回填原文、来源哈希和字符区间；
4. 程序校验数量、类型、去重和引用关系；
5. 多证据问题必须关联多个父块；
6. 每段证据必须能够精确回查原文。

因此，生成数据应表述为“AI 基于真实证据生成并由程序校验”，不能表述为人工标注。

## 消融方法

```text
BM25
Embedding
BM25 + Embedding + RRF
BM25 + Embedding + RRF + Rerank
```

- BM25 验证关键词检索基线；
- Embedding 验证语义召回；
- RRF 验证稀疏与稠密召回的互补性；
- Rerank 验证候选前置和排序收益。

## 主指标

| 指标 | 含义 |
| --- | --- |
| `Hit@K` | 前 K 条是否至少包含一个正确父块 |
| `Evidence Recall@K` | 前 K 条覆盖了多少标注证据 |
| `MRR` | 第一个正确结果是否足够靠前 |
| `P95 Latency` | 在线链路的尾延迟 |

NDCG、Precision、普通 Recall、调用量和逐题明细保留在机器报告中用于排错，不要求全部对外展示。

检索 Hit 不能称为回答准确率。最终回答还需要 Faithfulness 评测，无答案样本则需要单独计算 Evidence Gate 的动作准确率。

## 参数策略

项目先固定一套适合中文技术 Markdown 的父子分块与召回参数，不使用当前评测集进行大规模网格搜索。只有错误案例出现稳定模式时，才调整 Chunk、Top-K 或上下文预算，以减少过拟合和无效在线调用。
