# Phase 5 分布式改造 —— 事后总结

- 决策依据：[ADR-0006](../adr/0006-distributed-runtime.md)
- 状态：Stage 0–7 全部完成；部署形态最终定为**单实例多进程**

这份文档原本是实施计划。改造完成后改写为事后总结：**实际做成了什么样、哪里和计划不一样、还剩什么**。每段的具体改动看提交记录，选型取舍和踩的坑看对应的 ADR。

---

## 最终形态

```
浏览器 ──HTTP/SSE──> zhiyu (FastAPI，1 个)
                        │
        ┌───────────────┼───────────────┐
        ▼               ▼               ▼
     MySQL 8         Redis 7        ChromaDB
     业务数据    队列/事件流/锁/信号    向量检索
        ▲               ▲
        └───────┬───────┘
                │
    ┌───────────┼───────────┐
    ▼           ▼           ▼
索引 worker  转写 worker  Agent worker
 arq:index    arq:asr     arq:agent
 并发 10       并发 4       并发 4
```

计划里写的是「`zhiyu-api × N`（无状态）+ Nginx」，实际是**单实例 + 3 个 worker 进程**。多实例的能力实现并验证过，但按项目定位没启用。

三个队列分开的理由是**时长与性质**：索引几百毫秒，转写和 Agent 运行可能跑满 180 秒。混在一起时，长任务会占住并发名额，让短任务干等。

## 计划与实际的偏差

### 1. BM25 词表外置 → 只放版本号

原计划把分词结果序列化进 Redis，省掉每次启动的重建。

**实测推翻了这个前提**：973 个分块全量重建只要 **399 毫秒**（拉数据 175ms + jieba 分词 216ms + 构造 8ms）。快照只能省掉分词那约 211 毫秒，却要背上序列化格式兼容、反序列化安全面、写入侧分布式锁。

结论是**负收益**。最终方案：词表仍留在各进程内存里，Redis 上只放一个**版本号**，谁改了索引就 +1，各进程检索前比对、落后就自己重建。

顺带修掉一个真 bug：BM25 内部两个平行列表靠下标对齐，删除文档的三步操作不是原子的，并发下会错位并**安静地返回错误文档**。

### 2. 「索引任务改为写入时入队」——入队早就做了

计划写的是「写页面时直接投递任务，取消轮询」。读代码发现**入队早就实现了**——写页面时已经在同一个事务里把任务写进表。

要改的不是「入队」，是**消费方式**。按计划的理解去做会做出重复入队或破坏事务一致性的改动。

最终确立的原则：**表是任务的真相来源，队列只是让它更快被执行的通道**。队列会丢，表不会；重试、恢复、审计的语义本来就围绕表设计。

### 3. Stage 6 记的「已知坑」不成立

计划里写着：改造后 `timeline` / `retrieval_stats` / `model_usage` 三个字段会静默变空，因为它们依赖请求上下文，而 worker 没有。

读代码后确认**不成立**：这三个字段来自运行结果本身（`run.response`），和请求上下文无关；而且「写数据库」和「执行」始终在同一个进程里。已用测试把这个结论钉住。

**教训**：计划里的「坑」也要核实——写计划的人可能基于当时的理解写下因果链，而代码实际的结构未必支持那个推断。

### 4. Stage 4 记的两笔账都不实

- 封装泄漏不是 2 处，是 **6 处**（跨 4 个文件，其中 2 处是吞掉错误的防御性 `getattr`）
- per-request 线程池不是 4 处，是真正 **2 处**（另外两个「建池点」是死代码和不可达分支）

### 5. 心跳做了又删

多实例下，worker A 重启会把 worker B 正在跑的运行误标记为失败。当时的解法是**心跳**：执行期间每 30 秒往数据库写一次时间戳，启动恢复只回收心跳过期的。

真开多实例验证过它有效（并发 10 个真实对话时重启一个 agent worker，另一个上的 6 个零误伤）。

但**最终删掉了**：项目定为单实例后，worker 只有一个，它重启了就等于库里所有 `running` 都是它上次跑挂的，**全部回收本来就对**，不需要区分。字段、续期循环、相关测试一并删除。

### 6. 分发层与选主锁也删了

同理由：单实例只有一个 API，不需要 nginx 分发；定时清理只有一份进程，不存在「抢」。

代码能力保留（事件流、取消信号、会话锁都在 Redis 上），需要多实例时再加上部署层即可。

### 7. 测试方言最终统一到 MySQL

计划里写的是「新增 `test/integration/mysql/` 覆盖方言敏感点，单元测试继续用 SQLite 保持秒级」。

实际做法更进一步：**SQLite 彻底移除**，所有测试连真实 MySQL 上的独立测试库 `zhiyu_test`。代价是跑测试前必须先起容器，换来的是测试与生产方言完全一致。

移除时撞出一个真 bug：**baseline 迁移的 downgrade 在 MySQL 上跑不通**——那条「先删索引再删表」的序列是 Alembic 在 SQLite 环境下 autogenerate 生成的，MySQL 不允许删除被外键需要的索引（错误 1553）。原先靠 `render_as_batch` 掩盖着。

### 8. 本地模型全部移除

计划里只提了移除本地 whisper。实际把本地 Embedding 和 Rerank 后端也移除了，统一走模型网关。理由一致：多进程下每个进程各加载一份模型不划算，而用来限并发的信号量只在单进程内有效。

**删之前必须核实向量集合名**：集合名是「Provider + 地址 + 模型 + 维度」的哈希，换一个就等于换了个集合，已有向量看起来会「消失」。正因为如此，`EMBEDDING_PROVIDER` 字段保留但取值收窄为单一选项——它是哈希输入的一部分。

## 遗留事项

### 技术债

- 根目录 11 个 LeetCode 练习文件（未跟踪）——移出项目目录
- `frontend/legacy/` 4 个死 HTML 文件——删除
- `package-lock.json` 与 `pnpm-lock.yaml` 二选一
- `frontend/src/styles/index.css` 3562 行——拆分
- 前端 4 个 tab 无路由，刷新丢状态——引入 react-router
- 检索线程池缺正式的 `shutdown` 钩子
- Docker 那条启动路径没配 `stop_grace_period`（本地启动有 30 秒优雅宽限期，容器里用的是默认 10 秒）

### 线程池治理（未做）

现状是四个池各自为政：anyio 的池（40，服务同步端点）、asyncio 默认池（`min(32, cpu+4)`，服务所有 `to_thread`）、检索池（8）、Agent 执行池（4）。

问题在于 **asyncio 默认池里混着慢任务（LLM 调用、BM25 全量重建）和快任务（数据库读写）**，慢任务会饿死快任务。理想做法是新增 `core/executors.py` 按用途分池。

**必须一并计算的约束**：线程总数上限 ≤ 数据库连接池容量。默认池 32 线程 vs `pool_size=10 + max_overflow=20 = 30`，会打爆连接池，表现为随机的 `QueuePool limit ... connection timed out`，而且难以复现。

### 进程内缓存（不打算改）

四处进程内 LRU/TTL 缓存（Embedding 查询、Query Rewrite、检索结果、CRAG 评分）。单实例下它们是纯粹的性能优化，没有一致性问题。

### 未开工

**Stage 8：拆分文档解析服务**。把 pdfplumber / python-docx 拆成独立服务，主 API 镜像能小很多。收益是镜像瘦身，成本是多一个服务 + 一次网络跳转 + 文件传输方案。优先级不高——除非镜像体积成了实际问题。
