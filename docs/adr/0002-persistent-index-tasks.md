# ADR-0002：持久化异步索引任务

- 状态：已采用
- 日期：2026-08-04
- 更新：2026-10-14 —— 执行者由进程内 Worker 换成 arq worker 进程

## 背景

Embedding、Reranker 或 ChromaDB 不可用时，同步索引会让用户无法保存知识。

## 决策

页面事务只创建 `WikiIndexTask`；事务提交后立即投递到 arq 队列，由独立的索引 worker 进程消费；worker 每分钟还兜底扫描一次，补投漏掉的任务、回收卡死的任务。

任务记录状态、尝试次数、下次执行时间和锁定时间。失败按表上的 `next_attempt_at` 指数退避重投，**不使用队列自带的重试机制**——两套退避并存时，实际间隔取决于谁先到，线上就说不清一条任务要等多久。

**表是任务的真相来源，队列只是让它更快被执行的通道。** 队列会丢（进程在投递后退出、投递时网络抖动），表不会；而且重试、恢复、审计的语义本来就围绕表设计。

## 结果

- 主数据写入不依赖模型可用性，也不依赖队列可用性——投递失败只记日志，任务留在表里等兜底扫描。
- 索引延迟由平均 2.5 秒（5 秒轮询周期的一半）降到毫秒级。
- worker 崩溃后任务不会永久停在 `processing`：兜底扫描按锁定时间回收。这一点必须由 worker 做而非 API——执行已经搬到独立进程，API 重启时 worker 可能还活着。
- 代价是任务写两次（表 + 队列），但两边职责清晰：表保证不丢，队列保证快。
- 并发抢占改为一条 `UPDATE ... WHERE status IN (...)` 原子操作，按影响行数判断是否抢到。原先的「读—改—写」三步在多 worker 下会让同一页面被索引两次。
